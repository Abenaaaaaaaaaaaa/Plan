## 1. 背景、目标与非目标

### 1.1 背景

v1.0 是一套 8 屏 UX 流程稿（首屏空态、新建计划、计划列表、计划详情、执行记录、计时、日历汇总、我的）。现状稿的流程主线可以走通，但存在三类结构性问题，直接导致结论不可信、数据不可对账：

1. **同一屏内数字自相矛盾**。v1.0 计划详情屏同时展示「当前执行进度 10.23%」「执行计划天数 57天/365天」「完成计划天数 26天/365天」「距离结束 275天」。按 365 天反推 10.23% 应约为 37 天，与 26、57 均不符；57 + 275 = 332 也不等于 365。没有唯一口径，任何进度展示都无法被用户验证。
2. **"每天必做"与"区间内任意天执行"两种产品定义混用**。列表卡片的「距离结束 275天」暗示每天都欠账，记录面板的两态图例（完成 100% / 执行但未完成）又暗示每天都要交代，而产品实际允许任意天执行。
3. **计时不可靠**。计时页只有一个「开始/暂停」合并按钮，无本次/今日累计回显；无跨天规则；删除为永久删除且无二次确认与撤销（现状稿自己写明"数据无法恢复"）。

### 1.2 目标（可观察，不含量化承诺）

- **可对账**：任一计划在任意时刻，完成度、已执行天数、达标天数、应完成/已投入/落后三组数字必须能被同一套公式互推，用户与客服可用手算验证。
- **可完成**：用户从"打开小程序"到"开始为某个计划计时"不超过 2 次点击（列表卡片上的开始按钮直达计时）。
- **可恢复**：计时在切后台、锁屏、杀进程、跨零点四种中断下都不丢失已发生的有效时间，且用户可修正被误判的时长。
- **可追溯**：每条时长记录能回答"哪一天、从几点到几点、是计时还是补录、是否由跨天拆分产生"。

### 1.3 非目标（本期明确不做）

- 不做"每天必做/连续打卡/断签惩罚"类机制（与"区间内任意天执行"定义冲突）。
- 不做社交、排行、计划分享、模板市场。
- 不做提醒推送与订阅消息（见 §4 范围）。
- 不做多端同步的账号体系（本期按设备本地 + 云端备份实现，不做登录态冲突合并）。

## 2. 目标用户与核心场景

### 2.1 目标用户

**以"一段周期内的累计投入"为目标的自学者**，典型是备考、技能学习、语言学习、写作/练习类长期投入。他们的特征：

- 计划周期以月/季/年计（30–365 天），不按"每日打卡"计。
- 允许某几天完全不学（工作忙、出差），但不能接受"断签清零"。
- 关心两件事：**总共投了多少**（累计时长）、**现在落后没有**（应完成 vs 已投入）。

### 2.2 核心场景（P0 旅程）

| 场景 | 触发 | 用户动作序列 | 完成证据 |
|---|---|---|---|
| **S-A 首次建计划并开始** | 首次打开小程序 | 计划页空态 → 「新建第一个计划」→ 填名称/每日目标/区间 → 保存 → 列表出现该卡片 → 点卡片上 ▶ → 计时页「开始」 | 列表卡片显示「进行中 · 今日 0/60 分钟」，计时页计时环开始走字 |
| **S-B 日常学习（高频）** | 想起要学 | 打开小程序落在计划页 → 点目标卡片 ▶ → 计时 → 「结束」→ 结果卡 | 结果卡显示「本次 12 分钟 · 今日 44 分钟 · 已达标」，回到详情后完成度与今日数字同步更新 |
| **S-C 中场休息** | 学习被打断 | 计时页「暂停」→ 做别的事 → 回来「继续」→ 「结束」 | 暂停期间不计入任何数字；恢复后计时环从暂停值继续 |
| **S-D 忘记计时** | 想起来昨天学过但没计时 | 详情/记录面板 → 「手动补录」→ 选日期 + 填分钟 → 保存 | 记录面板与日历上该日出现"补录"标识，完成度按补录后重算 |
| **S-E 复盘欠账** | 月底/周末 | 计划页 → 卡片（看到"落后 20h"）→ 详情 → 记录面板 → 日历 | 辅助指标行显示「应完成 120h / 已投入 100h / 落后 20h」；记录面板能定位到具体哪几天没有记录 |
| **S-F 计划结束** | 区间走完 | 打开小程序 | 卡片徽标变「已结束」或「已过期」；详情底部主按钮变「再建一个」；可导出记录 |

### 2.3 关键约束（来自现状）

用户已有的一批计划（v1.0 的 A/B/C 计划）为 mock 数据。本期**不做数据迁移**，v2 上线后用户需重建计划；如后续需要迁移，另立需求。

## 3. 名词与计算口径（全文档唯一口径）

> 本章是全文档唯一的计算定义来源。功能章节只引用名称，不重复定义。所有示例数字都由本章公式反推得到，见 §3.6。

### 3.1 名词

| 名词 | 定义 |
|---|---|
| **计划 plan** | 一段固定区间内、以一个每日目标时长为基准的投入容器。区间固定后不再自动延长。 |
| **计划天数 plan_days** | 计划的容量天数，用于计算目标总量。 |
| **每日目标 daily_target** | 用户为每个"有效日"设定的目标分钟数。 |
| **目标总量 target_total** | `daily_target × plan_days`，即完成度的分母。 |
| **有效片段 segment** | 一段连续、未被暂停切断、且不跨越本地零点的时间记录。是时长的最小记账单位。 |
| **累计有效分钟 accumulated_min** | 某计划所有有效片段（归属日期在计划统计窗口内）的分钟数之和，即完成度的分子。 |
| **完成度 completion** | `accumulated_min / target_total`，唯一百分比指标。 |
| **已执行天数 active_days** | 有任一有效片段（>0 分钟）的天数。 |
| **达标天数 met_days** | 当日累计分钟 ≥ 每日目标的天数。 |
| **已过天数 elapsed_days** | 从计划开始日到今天（含今天）的天数，上限为 plan_days。 |
| **应完成 due_min** | `elapsed_days × daily_target`，滚动口径，只用于辅助指标。 |
| **落后 gap_min** | `max(0, due_min - accumulated_min)`，只用于辅助指标。 |
| **补录 manual** | 用户手工填入的历史时长，标记来源为手动，需在三个界面可辨识。 |

### 3.2 日期口径（唯一，已锁定）

- **计划统计窗口 = `[开始日期, 结束日期]`**，即**开始日与结束日均计入**。
- **计划天数 = 结束日期 − 开始日期 + 1**（日差 + 1）。

由此，`2026-11-01 → 2027-10-31` 记为 **365 天**，目标总量 `1h × 365 = 365h`。

> 口径提示：`2026-11-01 → 2027-10-30` 只有 **364 天**，不得用作示例。本口径已由产品拍板锁定，全文档示例与验收数字均基于"含首尾"计算，不再保留第二套算法（剩余风险见 §12.2 R1）。

### 3.3 完成度

```
accumulated_min = Σ segment.duration_min   （segment.plan_id = 本计划
                                           且 segment.local_date ∈ [start, end)
                                           且 segment.void = false）
target_total   = daily_target(分钟) × plan_days
completion     = accumulated_min / target_total        // 不截断
展示值          = 保留 1 位小数，四舍五入
```

- **不为零保护**：`target_total` 恒 > 0（每日目标最小 1 分钟、计划天数最小 1 天），不存在除零。
- **超额**：`completion > 100%` 时，**数字继续上涨**（可显示 109.6%），**进度条填充封顶 100%**，进度条右侧增加文字「已超额 35h」。
- **分母固定**：`target_total` 在计划创建时确定，中途**不随日期流逝增长**。修改每日目标或区间后按新值重算（见 §3.7）。

### 3.4 已执行天数与达标天数

```
active_days = COUNT(DISTINCT local_date)  where day_sum > 0    且 local_date ∈ [start, end)
met_days    = COUNT(DISTINCT local_date)  where day_sum ≥ daily_target  且同上
```

约束（可作为单元测试断言）：

```
met_days ≤ active_days ≤ plan_days
completion ≠ met_days / plan_days        // 任意天可超额，两者不等价，禁止互相换算展示
```

### 3.5 应完成 / 已投入 / 落后（B 方案辅助指标）

```
elapsed_days = min(plan_days, 今天 − 开始日期 + 1)      // 今天在窗口内时按日累计
due_min      = elapsed_days × daily_target
invested_min = accumulated_min                          // 与完成度分子同源，必须一致
gap_min      = max(0, due_min − invested_min)
```

- 三者与主进度**同屏展示但视觉次级**（主进度在上，辅助指标在其下一行，字号小于主数字）。
- **主进度不因辅助指标倒退**：`completion` 只增不减（除用户主动改目标/区间）。
- `gap_min = 0` 时该行显示「已跟上应完成进度」，不显示 0h。

### 3.6 唯一示例数据集（全文档复用，必须可互推）

| 项 | 值 | 反推校验 |
|---|---|---|
| 计划区间 | 2026-11-01 → 2027-10-31 | 含首尾 |
| 计划天数 | **365 天** | 日差 + 1 |
| 每日目标 | **60 分钟（1 小时）** | — |
| 目标总量 | **365 小时（21,900 分钟）** | 60 × 365 |
| 今天 | **2027-02-28**（计划第 120 天） | 11-01 起算含首日 = 120 |
| 已过天数 | **120 天** | 今天 − 开始日 + 1 |
| 应完成 | **120 小时** | 120 × 60min |
| 累计有效分钟 | **6,000 分钟（100 小时）** | 见下 |
| 完成度 | **27.4%** | 6000 / 21900 = 27.397% → 27.4% |
| 已执行天数 | **80 天** | 60 达标天 + 20 未达标天 |
| 达标天数 | **60 天** | 60 × 90min = 5,400min |
| 未达标天数 | **20 天** | 20 × 30min = 600min |
| 累计校验 | 5,400 + 600 = **6,000 分钟** | ✅ |
| 落后 | **20 小时** | 120h − 100h |

**互推关系（评审时可现场验算）**：`27.4% × 365h ≈ 100h`；`6,000min ÷ 60min = 100h`；`60天×1.5h + 20天×0.5h = 100h`；`120h − 100h = 20h`。

> 该数据集覆盖"超额与不足混合"的真实分布（60 天超额、20 天不足、40 天空白），因此 v1.0 的三个矛盾数字在本数据集下**不可能再出现**。

### 3.7 目标/区间变更后的口径

- 修改 `daily_target` 或 `start_date`/`end_date` 后，`target_total` 重算，`completion` 立刻按新分母计算（会跳变）。
- 保存前必须弹出确认，明示跳变前后的数值（见 §6.2 编辑态文案）。
- 每次变更递增 `target_version`，详情页在完成度下方显示一行灰字：「目标已于 2027-01-15 由 1 小时调整为 30 分钟」，避免用户误判为数据出错。
- `start_date` 不得早于该计划**已有记录的最早 local_date**，否则会把历史片段挤出统计窗口（静默丢数）。违反时禁止保存并提示。

### 3.8 舍入与单位

- 单片段分钟数：`duration_min = floor((ended_at − started_at) / 60000)`，**向下取整**，不足 1 分钟记 0 并保留记录（用于连续性展示，不参与分子）。
- 所有汇总（今日、累计、完成度）均以**整分钟**相加后计算，不允许先转成小时再相加（避免 0.5833h 类精度堆积）。
- 小时展示统一保留 1 位小数（`100.0h`），分钟展示为整数。

## 5. 信息架构与导航

### 5.1 结构

```
Tab 根 1  pages/plans            计划页（列表 / 空态，同一路由）
   ├─ pages/plan-form            新建 / 编辑计划
   ├─ pages/plan-detail          计划详情
   │    ├─ 顶部分段 Tab「计划概况」  S5 主体（整屏视图 1）
   │    ├─ 顶部分段 Tab「执行记录」  S6（整屏视图 2，非页内第 4 块）
   │    ├─ pages/manual-entry    手动补录（从详情/记录面板进入）
   │    └─ overlay 计时层         S7（全屏浮层，非独立页面，见 §9.3）
   └─ overlay 改名弹层 / 删除确认 / 撤销 Snackbar

Tab 根 2  pages/calendar         汇总页（月度日历）

独立页    pages/me               我的（从计划页头像进入，有返回）
          pages/agreement        用户协议
          pages/privacy          隐私政策
```

### 5.2 导航规则

| 规则 | 说明 |
|---|---|
| Tab 根不带返回 | 计划页与汇总页是 `switchTab` 页面，**不渲染返回按钮** |
| S1 不是独立页 | 首屏空态是计划页的**空态渲染分支**（同一路由、同一 Tab、同一底部栏）。空态下的「新建第一个计划」与列表态工具栏 `＋` 是**同一个 action**，全产品只有一个"新建计划"入口 |
| S6 不是独立页 | 执行记录是详情页的**第二个整屏视图**，由导航栏正下方的顶部分段 Tab 切换；**不能做成页内下方的内嵌面板**（首屏看不到，会被误判为切换失效），也**不带底部主按钮**（全页主按钮只在 S5 底部固定栏出现一次） |
| S7 是覆盖层 | 计时页为半透明遮罩上的全屏卡片，**不进入页面栈**，因此不受"页面栈 10 层"与右滑返回影响（见 §9.3） |
| 返回仅存在于 | 计划表单、计划详情、我的、补录页 |
| 层级深度 | 最深路径：计划页 → 详情 → 补录页 = 3 层，满足小程序栈限制 |

## 6. 功能需求

> 通用规则：所有时间以设备本地日期判定日归属；所有数字展示口径见 §3。状态矩阵中"适用"标记为 ✅，"不适用"为 —。

### 6.1 FR-S3 计划页（列表 + 空态）

#### 6.1.1 目的

用户落地页。回答"我有哪些计划、现在该学哪个、今天学了没有"，并支持一键开始计时。

#### 6.1.2 页面结构

```
[ 自绘导航栏 ]  我的计划
                 （右上留胶囊安全区 ≥ 96×32px，不放任何可点元素）
[ 工具栏 ]      ＋  头像            ← 位于导航栏下方右侧一行
[ 列表区 ]
   卡片
     行1  计划名称（≤10 字，超出省略）      [置顶标]  [状态徽标]
     行2  进度条（4px）                    27.4%
     行3  今日 32 / 60 分钟                          (▶ 圆钮)
     行4  累计 100h / 目标 365h                       （弱化）

> **设计理由（导航栏「更多」方案 · 本轮第 3 条）**：v1.0 把「更多」做成计划名右侧的裸文字按钮，一是视觉上像标题的附属物，二是它落在 `right:14px` 的横向区间内，与微信右上角胶囊（`right:8px`、宽 87px、高 32px，`top:52px`）**直接重叠**，窄机型上必然被压住。
>
> 采用方案：**保留在导航栏内，但改为胶囊安全区左侧的图标药丸 `(⋮)`**（描边、白底、30×28px，`right:104px`），同时让标题在存在右侧动作时左对齐并限宽（`max-width: calc(100% - 194px)`）。
> 选择理由：(a) 改名/导出记录/删除是**计划级动作**，在两个分段 Tab 下都必须可达，若把入口下移到"导航栏下方一行"，它会占据切换 Tab 旁的位置、且在「执行记录」视图里显得像该视图的操作；(b) 药丸右边界恒在距屏幕右侧 104px，胶囊左边界在距右 95px，二者保留固定 9px 间隙，375px 与 320px 下都不相交（实测包围盒见 §9.2）；(c) 图标用 `⋮`（竖直三点）而非 `⋯`（水平三点），避免与胶囊自身的「⋯」图标视觉重复，用户不会误点胶囊。
> 动作可达性：点 `(⋮)` 弹出 ActionSheet，含「改名 / 编辑」「导出记录」「删除计划」三个动作（另加「取消」），两个 Tab 下均可点；「导出记录」仍不进底栏（见 §6.3.5 约束）。补录不从该菜单进入，入口在执行记录视图的「＋ 手动补录」。

> **设计理由（评审问题 1 · 切换可见性）**：v1.0 把「执行记录」做成页面内第 4 块的内嵌 Tab，用户点「执行记录」时首屏（可视区顶部）仍是块1–块3，只有向下滚动才看到内容，"点了没反应/切换失效"是必然误判。改为导航栏正下方的顶部分段 Tab 后，两个 Tab 是**互斥的整屏视图**（不是滚动定位）：切到「执行记录」时首屏第一行就是图例、紧接着当月网格，内容差异在同一屏内肉眼可辨。
> **设计理由（评审问题 1 · 唯一主操作）**：今日条右侧的「开始计时」与底部固定栏的「开始计时／继续计时」是**同一 action 的两个入口**，同名按钮两处出现会让用户猜"点哪个、有什么区别"，且两个入口的状态可能不同步（例如计时中只有一处变成"继续计时"）。保留底部固定栏（拇指热区、与 S2/S7 的底部主操作位置一致），今日条降级为纯数字展示；运行态反馈由底栏按钮文案承担（「继续计时」即表示已有进行中片段）。

#### 6.4.2 页面结构

> 承载形式：本视图是 S5 详情页的**整屏第二视图**（顶部分段 Tab「执行记录」），不是页内第 4 块的内嵌面板。切到该 Tab 后，**首屏（不滚动）必须是「图例 + 当月月份块」**，不做折叠、不做「展开更多」。

```

#### 6.4.3 规则

- **三态**：`day_sum ≥ daily_target` → 达标（绿）；`0 < day_sum < daily_target` → 有记录未达标（黄）；`day_sum = 0` → 无记录（灰）。
- **补录标识**：该日存在 `source = manual` 或含 manual 片段时，色块右下角加 3px 圆点，并在点开日详情中标注「含补录 20 分钟」。
- **手动补录的输入与按钮（本轮第 6 条）**：
  - 时长输入框为「数字 + 固定单位后缀『分钟』」的组合控件（后缀带分隔竖线、不可编辑），**禁止出现无单位的裸数字**；范围 1–720 分钟。
  - 输入下方实时给出中文时长预览，**必须带单位且口语化**：`20` → 「= 20 分钟」；`90` → 「= 1 小时 30 分钟」；`60` → 「= 1 小时」；`0` → 「= 0 分钟」且保存置灰。
  - 保存入口是**描边次级按钮**「✓ 保存补录」（白底 + 1px 描边 + 勾图标，高 38px、圆角 9px），与底栏主按钮「开始计时 / 继续计时 / 再建一个」（黑底、46px 高）形成明确主次：颜色、高度、位置三重区分，不得用纯文字链。
  - 取消仍为文字链（左侧、次级），保存按钮靠右；弹层底部不再出现第二个黑底主按钮。
- **区间外**：`local_date` 不在 `[start, end)` 的格子显示为「—」，不参与任何统计。
- 月份必须**连续倒序**（v1.0 出现 12月→11月→9月跳月，缺 10 月）。
- 单格可点击 → 日详情弹层：列出该日所有片段（时间段、分钟、来源、是否跨天拆分），并提供「补录/修正」入口。
- 视觉折算：月度块内每天一格，与真实周对齐；v1.0 的"9 列 × 3 行"不对应任何真实月份，无法定位到日。

### 6.6 FR-S8 汇总页（月度日历）

#### 6.6.1 页面结构

```
[ 自绘导航栏 ]  汇总                     （无返回）
[ 月份头 ]   ‹  2027年2月  ›            右侧「本月」
[ 周头 ]     一 二 三 四 五 六 日
[ 日历网格 ]  7 列，gap 6px；375px 下每格 44.4×48px，320px 下 36.6×48px
  每格自上而下（padding 3px）：
    第1行（高 12px）：日期数字（左，11px 600，行高 12px，不换行）
                     +N（右，8px 灰，仅任务数 > 3 时出现，与日期两端对齐）
                     补录蓝点（4px）紧贴日期数字右侧
    第2–4行：任务标识条，每条一行（行高 8px、行距 2px），最多 3 行
       [1–2 字任务标识，8px 灰，固定 8px 宽] + [3px 高微进度条]
         条长 = min(100%, 该任务当日分钟 ÷ 该任务 daily_target)，最低 8% 保证可见
         颜色 = 绿（该任务达标）/ 黄（该任务有记录未达标）
    无记录 → 格内无条，只有日期数字
    今天 → 内描边 2px（#111），不改变底色
    区间外 → 透明底、无描边
[ 图例 · 单行 ]  ■ 达标   ■ 未达标   (?)   点击日期查看当天详情
                     ↑ ? 气泡承载次要说明（补录 / 区间外 / 条长口径）
[ 底部 Tab 栏 ]  [计划]  [汇总]
```

> **设计理由（评审问题 2 · 为什么颜色下沉到任务级）**：v1.0 用单一颜色表达"当天是否达标"。但一天可能有 2 个任务、一个达标一个不达标，单色格只能二选一，等于把这个事实抹掉；而且用户必须点某天才知道"那天做了什么"。改用**每任务一条标识条**后，格内同时表达"有几个任务、各做了什么、各自到什么程度"——条长是完成度，颜色是状态，任务身份由 1–2 字标识承担。
>
> **取舍（必须写死的边界）**：**放弃用格子底色表达"这天整体是否达标"**，底色回归中性（只有"今天"和"区间外"两种可区分）。原因有三：(a) 与任务级颜色形成双重编码冲突（同一格既黄又绿）；(b) 多计划重叠时"整体达标"在"区间内任意天执行"口径下没有定义（各任务目标不同）；(c) 底色一旦被赋予达标含义，后续任何人都会想再往回加。要看"这天整体如何"，点开日详情看任务清单，答案比一个颜色更准确。
>
> **一次最多 3 条 + `+N`（本轮第 1 条）**：从 2 条提到 3 条，需要先解决"3 条会不会把日期数字和 `+N` 挤出格子"。做法是**先压缩、再加高，两步都做完**：
> 1. 压缩内容：任务条行高 9px → 8px、行距 3px → 2px、日期行 13px → 12px、任务标识字号 8px、条高保持 3px（仍可辨认）。
> 2. 加高格子：`min-height` 46px → **48px**（仅增加 2px，而不是按 3 条线性增加 9px），因为第 1 步已回收 5px。
>
> 最终尺寸（实测，Chrome 真实盒模型）：**375px 宽：每格 44.4×48px；320px 宽：每格 36.6×48px**。3 条时内容高度 = 3(padding-top) + 12(日期行) + 2(间隙) + 3×8 + 2×2(条间距) + 3(padding-bottom) = **45px ≤ 48px**，无纵向溢出；日期数字「23」与右上 `+1` 的包围盒水平间距 375px 下 16.2px、320px 下 8.3px，均不相交。
>
> 为什么不再往 4 条加：320px 下每格只有 36.6px 宽，4 条需要 55px 高、且日期行与 4 行任务条会逼近底部 Tab 栏的可视预算；超出部分折叠为 `+N`，点日期仍在日详情完整列出（`+N` 与日期数字两端对齐，互不侵占）。
>
> **底部说明压到 1 行（本轮第 2 条）**：常驻说明只保留两类必要信息——**图例含义**（`■ 达标` / `■ 未达标`）和**下一步动作**（「点击日期查看当天详情」），合并为单行，实测高度 38.1px（padding 10+12 + 单行 16）。
> 次要说明一律移出常驻区，改由图例中的 `?` 气泡承载（点开弹层「日历说明」）：
> - 「蓝点 = 含手动补录」
> - 「透明格 = 区间外；描边格 = 今天」
> - 「格子底色不表示这一天是否达标；条长 = 该任务的当日完成度；最多 3 条，超出显示 +N」
>
> 理由：这四句是**首次使用才需要读一次**的元信息，常驻会与日历本体争夺注意力（375px 下四行说明约占 72px 高度，等于压缩一整行日历）；放进 `?` 后，懂的人不被打扰，不懂的人随时可查。`?` 的可点区域 ≥ 15×15px，位于图例行内、不占额外高度。

#### 6.6.2 规则

- **逐任务渲染**：一个格子内按任务渲染标识条，只渲染"当日有记录（`day_sum > 0`）"的任务；无记录的任务不占行（否则空白日会被噪点铺满）。
- **状态定义（任务级，不是日级）**：`该任务当日分钟 ≥ 该任务 daily_target` → 达标（绿条）；`0 < 当日分钟 < daily_target` → 有记录未达标（黄条）；`= 0` → 该任务无条。
- **条长**：`min(100%, 当日分钟 ÷ daily_target)`，向下取整到整数百分比；最短 8%（1 分钟也要可见，但不得伪装成有进度）。
- **排序**：未达标任务优先排在前面（落后更值得被看见），其次按计划创建顺序；**最多显示 3 条**，其余折叠为 `+N`（N = 被折叠的任务数，仅任务数 > 3 时出现）。
- **日期数字必须保留**：位于格子左上角，任何条数下都不省略；`+N` 位于右上角，与日期数字对角分离，**不得挤压日期数字**（375px 与 320px 实测包围盒均不相交，见 6.6.1）。
- **底色中性**：不做日级达标着色；今天用内描边区分、区间外用透明区分，两者都不代表达标状态。
- **示例日（原型与本文必须一致，用于对比密度）**：
  - **2027-02-24 · 一天 2 个任务（常规密度）**：A计划 30 分钟（目标 60 → 黄条 50%）＋ 冲刺计划 60 分钟（目标 60 → 绿条 100%）→ 格内 2 条，一黄一绿，无 `+N`。
  - **2027-02-23 · 一天 4 个任务（触发 `+N`）**：A计划 90 分钟（绿 100%）＋ 冲刺计划 110 分钟（绿 100%）＋ B计划 20 分钟（目标 45 → 黄 44%）＋ 日语计划 25 分钟（目标 30 → 黄 83%）→ 未达标优先 → 显示 B（黄 44%）、日语（黄 83%）、A（绿 100%）＋ 右上「+1」（被折叠 = 冲刺计划）。
  - **2027-02-19 · 含补录（蓝点）**：A计划当日合计 90 分钟 = 70 分钟计时 + 20 分钟手动补录 → A 条绿（100%）；同日冲刺计划 170 分钟 → 绿（100%）→ 格内 2 条绿，日期数字右侧带 4px 蓝点；A计划总额与未拆分时一致（90 分钟），仅来源不同。
- **`+N` 的可发现性**：`+N` 不可单独点击，点击整格即打开日详情；日详情中列出被折叠任务，保证"折叠不等于丢失"。
- 点某日 → 日详情弹层：按计划分组列出「A计划 30m · 未达标 ›」「冲刺计划 60m · 达标 ›」，每项可跳详情；此处的"达标/未达标"同样按任务判定，不给出"这天是否达标"的合并结论。
- 月份左右切换；「本月」回到当月；未来日整格降透明度（0.35），不可点。
- 与记录面板（S6）共用同一份日汇总数据，**同一任务的当日分钟两处必须一致**；S6 是单计划视图（一天只有一个任务），因此仍用单色日块，两处编码不同但数据同源，不视为不一致。

## 7. 数据模型

> 本章为字段级定义，供开发与测试对照；不涉及接口协议与代码结构。

### 7.1 plan

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `plan_id` | string(36) | 主键，UUID v4 | 客户端生成，幂等 |
| `name` | string | 1–10 字符 | 去首尾空白 |
| `daily_target_min` | int | 1 ≤ x ≤ 720 | 单位分钟 |
| `start_date` | date | `YYYY-MM-DD` | 本地日期 |
| `end_date` | date | `> start_date` | 本地日期，**计入统计窗口（含首尾）** |
| `plan_days` | int（派生） | `end - start + 1` 日差 | 不落库，含首尾 |
| `target_total_min` | int（派生或冗余） | `daily_target_min × plan_days` | 冗余时须在每次变更同步 |
| `pinned_at` | timestamp/null | — | 排序用 |
| `deleted_at` | timestamp/null | — | 软删除，30 天 |
| `target_version` | int | 初始 1 | 每次目标/区间变更 +1 |
| `created_at` | timestamp | — | — |
| `updated_at` | timestamp | — | 列表排序用 |

### 7.2 segment（有效片段，唯一记账单位）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `seg_id` | string(36) | 主键 | — |
| `plan_id` | string(36) | 外键 | — |
| `started_at` | timestamp(ms) | 必填 | 服务端校准后的绝对时刻（UTC 毫秒） |
| `ended_at` | timestamp(ms) | 闭合时必填 | 必须 > `started_at` |
| `duration_min` | int | `floor((ended-start)/60000)` | 可 0（<1 分钟） |
| `local_date` | date | = `localDate(started_at)` | 归属日期快照，**不随时区重算** |
| `source` | enum | `timer` / `manual` / `midnight_split` / `recovered` | 补录 = `manual` |
| `close_reason` | enum | `user_end` / `user_pause` / `user_exit` / `app_kill_recovered` / `midnight_split` / `target_reached` | — |
| `parent_seg_id` | string/null | 跨天拆分时同源 | — |
| `split_seq` | 0/1/null | 拆分序号 | — |
| `client_id` | string(36) | 唯一键 | 幂等去重（重传不重复计数） |
| `void` | bool | 默认 false | 用户作废的段不进分子，保留审计 |
| `created_at` / `updated_at` | timestamp | — | — |

**必须成立的约束**

1. 一条片段**不得跨本地零点**（`localDate(started_at) === localDate(ended_at)`）。
2. 一条片段**不得包含暂停时间**（暂停即闭合）。
3. 同一 `plan_id` 下，**同时最多一条未闭合片段**。
4. `client_id` 唯一，重传不产生重复行。

### 7.3 daily_rollup（日汇总，冗余加速）

| 字段 | 类型 | 说明 |
|---|---|---|
| `plan_id` | string(36) | 联合主键 |
| `local_date` | date | 联合主键 |
| `minutes_sum` | int | 该日有效分钟（不含 `void`） |
| `seg_count` | int | 片段条数 |
| `has_manual` | bool | 是否含补录，供 S6/S8 标识 |
| `in_range` | bool | 是否落在 `[start,end)`，区间外仍记录但不进分子 |
| `updated_at` | timestamp | — |

规则：**明细是真相，rollup 可随时重建**；写入必须按 `client_id` 去重后 upsert，否则重传会把某日翻倍。客户端冷启动时校验最近 3 天 rollup 与明细是否一致，不一致则以明细重建。

### 7.4 状态判定

```
plan_days     = dateDiff(end_date, start_date) + 1        // 含首尾
target_total  = daily_target_min × plan_days
accumulated   = Σ duration_min(plan_id, local_date ∈ [start, end], void=false)
completion    = accumulated / target_total
active_days   = COUNT(DISTINCT local_date, day_sum > 0)
met_days      = COUNT(DISTINCT local_date, day_sum ≥ daily_target_min)
elapsed_days  = min(plan_days, dateDiff(today, start_date) + 1)   // 窗口内
due_min       = elapsed_days × daily_target_min
gap_min       = max(0, due_min - accumulated)
status        = 未开始   if today < start
                进行中   if start ≤ today ≤ end          // 结束日当天仍为进行中
                已结束   if today > end 且 accumulated ≥ target_total
                已过期   if today > end 且 accumulated < target_total
```

### 7.5 区间外片段

- `local_date > end_date` 或 `< start_date` 的片段：**保留记录、`in_range = false`、不计入分子**。含首尾口径下，结束日当天（`local_date = end_date`）正常计入。
- 典型来源：计划最后一日跨零点产生的次日段；用户把 `end_date` 往前改导致历史段落到窗外。
- 界面：记录面板该格显示「—」，日历该日不计入当月合计，任何入口都不提示"数据被丢弃"（避免用户误解为 bug），但在日详情弹层内以灰字标注「不在计划区间，不计入完成度」。

### 7.6 补录来源

- `source = manual`，`close_reason = user_end`。
- 补录必须选日期（不得晚于今天）与分钟数（1–720），可选备注（≤20 字，不进任何统计）。
- 同一日允许补录多条（视为不同片段），也允许对已有片段「修正」（生成一条 `void=true` 的原片段 + 一条新的 manual 片段，保留审计链）。
- 补录后：`daily_rollup.minutes_sum`、`has_manual`、`accumulated`、`completion` 全部重算；S5/S6/S8 同步刷新。

## 8. 计时状态机与边界规则

### 8.1 状态机

```
         ┌──────────┐   开始    ┌──────────┐   暂停    ┌──────────┐
         │ 未开始    │ ────────► │ 计时中    │ ────────► │ 已暂停    │
         └──────────┘           └──────────┘           └──────────┘
              ▲                    │    ▲                    │
              │ 作废/放弃           │    │ 继续               │ 结束
              │                    │    └────────────────────┘
              │                    │ 结束
              │                    ▼
         ┌──────────┐         ┌──────────┐
         │ 已结算    │ ◄────── │ 结果卡    │
         └──────────┘         └──────────┘
```

- 每个迁移都必须产生**已落库的片段**（暂停、结束、跨天、退出、杀进程结算）。
- 「开始」时若已存在未闭合片段（异常残留），先按 §8.4 结算该段，再开新段。

### 8.2 时间校准

- 进入计时层时请求一次服务端时间，记录 `offset = serverTs - Date.now()`。
- 之后所有 `now = Date.now() + offset`；判定跨天、计算时长均用校准后的时间。
- 目的：防改系统时间刷时长，防跨天误判。

### 8.3 后台 / 锁屏

- 逻辑层挂起后定时器不跑，**但只依赖时间戳**，回前台重算即正确，无需补偿逻辑。
- 心跳：`onShow` / `onHide` / 切 Tab / 前台每 30 秒写 `last_heartbeat_ts`（单键、单数字，避免写放大）。

### 8.4 杀进程 / 长时间后台

| 情形 | 判定 | 处理 |
|---|---|---|
| 短时重启（心跳 ≤ 5 分钟） | 心跳新鲜 | 静默续算，不提示 |
| 长时重启（心跳 > 5 分钟） | 心跳过期 | 以 `last_heartbeat_ts` 闭合，`close_reason = app_kill_recovered`，弹**结算确认卡**允许修改分钟数或作废 |
| 次日打开 | 未闭合 + 日期已变 | 先按 §8.5 补齐日切段，再按心跳闭合 |

### 8.5 跨零点分段

```
当 localDate(now) ≠ localDate(running_starts_at)：
  midnight = 次日 00:00:00.000（本地时区）
  segA = { started_at: running_starts_at, ended_at: midnight,
           local_date: D,   close_reason: 'midnight_split', source: 'midnight_split', split_seq: 0 }
  segB = { started_at: midnight, ended_at: null,
           local_date: D+1, split_seq: 1 }        ← 继续计时
  parent_seg_id 相同；running_starts_at 更新为 midnight（不打断用户）
```

- 前端每 30 秒检查一次（用户可能整夜不操作）。
- 连续多日未关（如睡了整夜又一天）：用同一纯函数 `backfillMidnightSegments(startTs, endTs)` 一次补齐 N 条，客户端与服务端**必须共用同一规则**，否则会出现 1 分钟差异导致日归属争议。
- 边界：若正好在 00:00:00.000 切换，不产生 0 秒段；`duration_min = 0` 的段仍保留但 `split_seq` 标记，仅用于连续性。

### 8.6 补录

见 §7.6。补录入口：记录视图的日详情弹层「补录」、记录面板空态按钮、计时层未开始态「手动补录」。导航栏 `⋮` 菜单只承载计划级动作（重命名 / 导出记录 / 删除计划），不放补录。

### 8.7 边界规则汇总（可直接转为用例）

| 边界 | 期望行为 |
|---|---|
| 暂停跨越零点 | 暂停先闭合（当日），继续时新开片段（次日），不产生跨天段 |
| 计时中改系统时间 | 校准后时间不跟随变化，时长不受影响 |
| 同一天多次开始/暂停 | 多条片段同 `local_date`，`day_sum` 相加 |
| 单段 < 1 分钟 | `duration_min = 0`，保留记录，不计入分子 |
| 计划最后一日计时跨零点 | 次日段 `local_date ≥ end_date` → `in_range = false`，不计入分子 |
| 达到目标后继续计时 | 允许；超额计入分子；进度条封顶、数字继续涨 |
| 删除计划时有未闭合片段 | 先结算该段（`user_exit`）再软删除 |
| 编辑区间导致历史段出窗 | 禁止：`start_date` 不得早于已有记录最早日期 |

### 9.3 手势冲突

| 冲突 | 处理 |
|---|---|
| iOS 右滑返回 vs 卡片左滑 | **放弃左滑删除**：左滑仅露「置顶」单个按钮；删除移入长按 ActionSheet。同时卡片左侧保留 24px 手势保护带 |
| 计时层返回 | 计时为**全屏覆盖层**（不进页面栈），返回由覆盖层自身的 ‹ 处理，规避系统右滑返回；退出前按 §6.5.5 三选一确认 |
| Tab 根 | 不渲染返回按钮，从根上消除"根页带返回"的歧义 |

### 9.4 存储容量与云端

**单片段体积**约 250 字节（JSON）。

| 场景 | 计算 | 年增量 |
|---|---|---|
| 1 计划 × 4 段/天 | 4 × 365 × 250B | 365 KB |
| 1 计划 × 6 段/天 | 6 × 365 × 250B | 548 KB |
| 5 计划 × 6 段/天 | 5 × 6 × 365 × 250B | 2.7 MB |
| rollup 冗余 | 5 × 365 × 60B | 110 KB |

**结论与要求**

1. 单 key 上限 1MB：若把全量明细存一个 key，1 计划约 2 年、5 计划约 4 个月即写不进去，**必须分片**。
2. 分片键：`seg:{planId}:{yyyyMM}`，单月单计划约 46KB，永不逼近上限，且可按月淘汰。
3. 本地只保留**近 90 天明细 + 全量 rollup + 计划元数据**（合计 < 500KB）；进入记录面板某月时按需拉取该月。
4. 同步读写在低端机会卡顿，禁止在首屏全量同步读取。
5. **云端为真相源**：明细表 + rollup 表；本地是缓存。换机/清缓存后可通过导入文件或云端恢复。

### 9.5 导出格式与现实限制

- `plans.json`：计划元数据（含 `target_version` 变更历史，用于解释进度跳变）。
- `segments.jsonl`：每行一条片段，固定字段 `plan_id, started_at, ended_at, local_date, duration_min, source, close_reason, void`。
- 体积参考：3 年 5 计划约 3MB。
- **限制**：小程序不能直接写入用户文件目录，只能写入沙箱后通过"分享文件"交给用户，或上传云存储生成下载链接。因此「我的」页文案必须是「导出记录（分享文件）」，**不得写"自动备份/换机一键恢复"**，否则形成错误预期。
- 导入：读取同格式文件，冲突以"较新 `updated_at` 优先"，`client_id` 去重。

### 9.6 性能

- 计划页首屏渲染 ≤ 300ms（本地缓存优先，后台静默刷新）。
- 日历月切换 ≤ 150ms（本地 rollup 渲染，缺月再拉）。
- 计时层渲染每 250ms 一次，仅更新文本节点，禁止整层重排。

### 10.2 关键指标（观测口径，不含目标值）

1. **建计划完成率** = `plan_create` / 进入表单次数。
2. **列表直达计时占比** = `entry=列表` 的 `timer_start` / 全部 `timer_start`（验证"2 次点击"设计是否被采用）。
3. **中断结算争议率** = `timer_recover` 中 `user_adjusted=true` 的占比；高于预期说明心跳策略不可信。
4. **补录率** = 含 `manual` 片段的计划数 / 活跃计划数；反映"忘记计时"的普遍程度，决定后续是否做提醒。
5. **误删撤销率** = `plan_delete_undo` / `plan_delete`。
6. **数字一致性错误率** = 客户端上报的 rollup 与明细重建差异条数 / 总计划数（应为 0）。

### 12.1 里程碑（不含排期承诺）

| 阶段 | 产出 | 退出条件 |
|---|---|---|

| M3 测试 | 边界用例回归（AC-08 ~ AC-13、AC-19） | 跨天/杀进程/补录三类零失败 |
| M4 提交审核 | 隐私政策/用户协议/客服入口齐备 | 审核通过 |

### 12.2 评审必须重点确认的三项风险

**R1 · 日期口径的连带一致性（已锁定为含首尾）**
本 PRD 已按左闭右闭实现：`plan_days = dateDiff + 1`，`2026-11-01 → 2027-10-31 = 365 天`，目标 365h，累计 100h → **27.4%**，应完成 120h、落后 20h。
风险不在口径本身，而在**实现时的边界疏漏**：结束日当天（`local_date = end_date`）必须计入统计窗口；只有 `local_date > end_date` 的跨天溢出段才算区间外。AC-10 与 AC-04 分别锁定这两条边界，开发与测试不得按"日差"旧口径取值。

**R2 · 辅助指标与主进度的视觉权重**
B 方案要求"欠账可见但主进度不倒退"。风险在于：示例中主进度 27.4%、落后 20h，两者放在同一块，用户可能只看"27.4%"而忽略欠账；也可能反过来被"落后 20h"压垮。需在原型阶段用两版排版（辅助行在进度下方 / 辅助行并入今日条）做用户验证，**不在此阶段定稿**。

**R3 · 杀进程"诚实结算"的用户信任成本**
按最后心跳结算，最坏情况会把整夜算成学习（8 小时）。虽然有结算确认卡，但用户若直接点「确认计入」而不看数字，会产生失真数据与对产品的不信任。需评估是否把默认值改为"作废、由用户手动补录"，或把确认卡改为默认聚焦在"调整分钟数"输入框。**这是产品价值观取舍，需产品负责人拍板。**
